WebTunnel Rebuild Plan

Refactor, don't restart — but the rewrite has to reach further down than it looks. A 16-week plan to turn a broken measurement into a thesis that cannot be attacked on its evidence.

Refactor. Starting from scratch would throw away the expensive part and keep the cheap mistake.

The costly assets — the master orchestrator, the model implementations, the evaluation and XAI modules, the LaTeX/figure export, the Docker topology — are all fine and would take two months to rebuild for no gain. What is broken is one architectural decision made in collect_scaled_dataset.py and sanitizer.py, and then inherited by everything above it.

But it isn't a patch either. The unit of analysis is wrong. Today a sample is "every packet on eth0 during a five-second window". It has to become "one TCP connection, with known identity". That change propagates into the split logic, the CV groups, the host aggregation, the defence simulation and the cascade — so layers 1 and 2 get rewritten outright, and layers 3 and 4 get surgical edits behind a new, stable data contract.

The plan below is roughly 55% keep, 30% rewrite, 15% delete. The long pole is not code — it is the capture campaign, which is mostly unattended and must not be started until the validation harness can fail it.

01

The single decision everything else follows from

Move ground truth from the parser to the collector, and make a connection — not a window — the atom of the dataset.

Right now sanitizer.py infers what it is looking at: which host is the client (from the first packet), which packets belong to the flow (all of them), where the handshake ends (first 0x17 byte). Every one of those inferences is wrong somewhere in the corpus, and the pipeline has no way to notice.

The collector, by contrast, knows everything: which class it is generating, which server and port it is talking to, which netem profile is active, which behaviour script is running, what the generator seed was, which git commit is checked out. It just never writes any of it down. So write it down — one sidecar JSON per capture — and the parser stops guessing.

contracts.py — the interface every other layer is written against
# emitted by the collector, next to every .pcap
CaptureManifest: capture_id, class, behaviour, profile, dest_id, client_stack,
                 target_5tuple, t_start, t_end, generator_seed, netem_params,
                 git_commit, target_duration_s, target_bytes_up, target_bytes_down

# produced by the flow builder, consumed by everything above
FlowRecord:
    flow_uid      # sha256(capture_id | 5-tuple | syn_ts) — the sample identity
    conn_id       # the TCP connection identity — THE grouping key for every split
    label, is_positive, behaviour, profile, dest_id, client_stack
    records       # [(t_rel, direction, tls_record_len)] after TCP desegmentation
    hs_end_idx    # index of the first true application record (client Finished + 1)
    n_up, n_down, bytes_up, bytes_down, duration
    provenance    # capture_id, git_commit, seed — every number traceable to a run

Two rules make the contract self-enforcing. A flow whose 5-tuple does not match target_5tuple is discarded, not analysed — that alone kills the cross-class contamination, the mDNS noise and the direction-inversion bug in one line. And conn_id is the only legal grouping key: splits, StratifiedGroupKFold and the host aggregator all take it, so the misalignment bug becomes structurally impossible rather than something you have to remember.

02

Keep, rewrite, delete

Be ruthless about the middle column and generous about the first — that is what makes this a refactor rather than a rewrite.

Keep as-is

  • architectures.py — plus a key-padding mask on the Transformer
  • train_xgboost.py, train_1d_cnn.py, train_transformer.py

  • traffic_generator.py → one Go client, one TLS stack, budget-driven sessions
  • sanitizer.py → 5-tuple demux, TCP desegmentation, TLS-record extraction
  • build_dataset.py → splits keyed on conn_id, four split axes
  • cross_validate.py → fix group alignment, inner-fold model selection
  • evaluate_before_after_defenses.py → record-level defences + adaptive adversary
  • netem_profiles.sh → ingress via ifb + rate ceiling
Delete

  • The 0x17 cutoff heuristic — replaced by hs_end_idx from the flow builder
  • recompute_tabular_features() — an artefact generator with no legitimate use
  • The DET curve's np.maximum(fpr, 1e-4) floor — plot to 1/N and stop
  • Every accuracy-first headline in the README

Roughly 3,000 of the repository's ~5,400 lines survive untouched. The rewritten modules are about 1,200 lines of Python plus ~350 lines of Go. That is two to three weeks of coding — the schedule is dominated by capture time, not by typing.

03

Six design principles for v2

Each one closes off a whole family of the findings from the audit, structurally rather than by vigilance.

  • Parity by construction, not by correctionOne Go binary generates all classes — HTTP/1.1 WebSocket, HTTP/2 fetch, HTTP/3 QUIC, and SOCKS5-through-Tor — using refraction-networking/utls with a single pinned HelloChrome_Auto profile. Configure the WebTunnel client with the same imitation. The ClientHello is then byte-identical across classes by construction, and a build gate asserts it. This replaces the roadmap's Mode A/Mode B choice with "both", and it is the highest-leverage change in the whole plan: about 350 lines of Go that permanently removes the TLS-stack criticism.
  • Session budgets are drawn from a shared distributionBefore each capture, draw a triple — target duration, target upstream bytes, target downstream bytes — from one common distribution, and pass it into whichever generator runs. Every class then has to hit the same budget. This makes total_pkts, total_bytes, duration and burst_count non-informative by design, which is the only clean way to kill the volumetric leak that currently gives 100% accuracy from four features. It also forces the negatives to be genuinely hard: a WebSocket session that must move 80 KB in 4 s looks structurally much more like a tunnel than one that sends six chat messages.
  • The dataset is guilty until proven innocentWrite the validation harness before the testbed work, and wire it into the build so it can fail. A dataset that does not pass the gates never reaches a model. This is the discipline that would have saved eight months, and reported deliberately in the thesis it becomes a methodological contribution rather than an embarrassment.
  • Strong features are not banned — they are justifiedThe tripwire must not push you into engineering away the 558 B invariant; that invariant is the real finding. The gate is: any single feature exceeding ~0.90 stump AUC must appear in an EXPECTED_INVARIANTS registry with a written protocol-level derivation and a citation. up_len_p50 = 558 = 5 + (514 + 22) + 1 + 16 passes that test. down_len_min = 80 (a ChangeCipherSpec record) does not, and must be eliminated. The registry becomes a table in the thesis.
  • Every experiment declares its adversary and its resolution floorTwo fields in every results JSON: adversary ∈ {static, adaptive} and n_negatives. The defence chapter reports both adversaries side by side. No plot may extend below 1/n_negatives, and no FPR is ever reported without a Clopper–Pearson interval. This turns the two weakest chapters into the two most rigorous ones.
  • Determinism in the lab, realism in a validation setToday the bridge relays into the live Tor network and three of the five WebTunnel targets are public sites (check.torproject.org, Wikipedia, DuckDuckGo — the other two resolve through an exit node and silently fail), while the negatives hit a local mock server. So content, RTT and reproducibility differ by class, in the positive class's favour. Fix it with a private Tor network (chutney: authority + 3 relays + your bridge, all in Compose) for the controlled corpus, and keep a smaller live-network set — same generator, same budgets — purely to show the findings transfer. That split answers "is your lab realistic?" without giving up reproducibility.
04

The capture campaign — design it before you run it

This is the critical path and the one thing you cannot fix afterwards. Size it from the claims you want to make, not from a round number.

Work backwards from the low-FPR claim

The assignment demands the low-FPR regime. By the rule of three, observing zero false positives in n negatives gives a 95% upper bound of 3/n. That fixes your negative-set size directly:

Claim you want to makeClean negative flows neededCapture time @ ~500/hVerdict
FPR ≤ 10⁻³3,0006 hTrivial — you already have this scale
FPR ≤ 10⁻⁴30,00060 hThe right target. 5–7 overnight runs
FPR ≤ 7.5 × 10⁻⁵40,00080 hComfortable margin; lets you say "below 10⁻⁴"
FPR ≤ 10⁻⁵300,000600 hOut of reach — report as analytical projection

Target: 40,000 negative flows and 8,000 positive flows. That buys a measured "FPR below 10⁻⁴ at 95% confidence" — a real result, stated at the scale the evidence supports — and 10⁻⁵/10⁻⁶ stay in the base-rate chapter as clearly labelled projections. Run four to six client containers in parallel against separate destinations to lift throughput; the bottleneck is docker compose exec round-trips, not the network.

The design matrix

Randomise the order across the whole matrix — never block by class again — and write one row of manifest.jsonl per capture.

Run a 2,000-flow pilot first, and be willing to throw it away

A pilot costs four hours and is the difference between discovering a design flaw in week 5 and discovering it in month 8. Run the full gate suite on the pilot. If a gate fails, fix the testbed and re-pilot. Do not start the 80-hour campaign until every gate is green on pilot data — that is the one process rule that makes this plan safe.

05

The build gates

checks/ is the first thing you write and the last thing you'd think to write. Six assertions, each mapping to a finding from the audit.

GateAssertionCloses
G1 · Stack parityClientHello record length and extension list are identical across all classes; JA4 hash is constant.F-02, F-03
G2 · Leakage tripwireNo single-feature depth-1 stump exceeds 0.90 AUC unless registered in EXPECTED_INVARIANTS with a protocol derivation.F-09
G3 · Null controlsLabel-shuffle AUC ∈ [0.45, 0.55]; same-generator/different-label AUC ∈ [0.45, 0.55].F-09
G4 · Budget parityTwo-sample KS test on duration, total_bytes, total_pkts between positive and each negative class: p > 0.01.F-06
G5 · Split integrityNo conn_id in two splits or two CV folds; group vector length and alignment asserted against the feature matrix.F-01, F-11
G6 · ProvenanceEvery flow's 5-tuple matches its manifest's target_5tuple; every capture has a manifest; drop reasons are logged and counted per class.F-04, F-08

G2 deserves a note on how it should feel in practice. On the first pilot it will fire, and it should — that is the harness working. The response is not to delete the feature but to ask why it separates. If the answer is a protocol invariant with an arithmetic derivation, register it and move on; that is your result. If the answer is "because my negatives are 5-second scripts and my positive is a saturated tunnel", the testbed has to change. The gate's job is to force that question every single build.

06

Sixteen weeks, three gates

Writing starts in week 5, not week 13. The theoretical chapters do not depend on any of this and are the cheapest insurance you have.

W1~30 h

Freeze v1 and build the harness

Tag the current repository as v1-audit — you will cite it in the thesis, so it must stay reproducible. Then write contracts.py and all six gates in checks/, with unit tests, against the existing dataset so you can watch them fail correctly.

OutputA harness that red-flags the current corpus — and the leakage-tripwire table that becomes a thesis figure.
W2–3~60 h

Testbed v2, part one — parity and isolation

  • The Go traffic client: uTLS HelloChrome_Auto, four transport modes, budget-driven sessions, deterministic seed
  • Configure the WebTunnel client with matching uTLS imitation; verify against upstream whether the bridge line needs an explicit option
  • Private Tor network via chutney in Compose; 3 bridge instances; 8 legit vhosts with distinct certs
OutputTwo flows from different classes whose ClientHellos are byte-identical. Screenshot it — that is a slide.
W4~30 h

Testbed v2, part two — capture correctness

  • Collector rewrite: one connection per sample, BPF-filtered tcpdump, sidecar manifest, randomised interleaving, parallel clients
  • ethtool -K offload off on the capture interface; verify no captured packet exceeds MSS
  • netem via ifb for ingress plus an htb rate ceiling per profile; generate PROFILE_DISPLAY_NAMES from the applied parameters
  • QUIC/HTTP-3 endpoint and class
OutputCollector that refuses to write a capture lacking a fresh SYN on an unseen source port.
W5~25 h

Pilot capture + flow builder

2,000 flows across the full design matrix. Write flow_builder.py (5-tuple demux, TCP desegmentation, TLS record extraction, hs_end_idx) and run every gate. Expect to iterate two or three times — that is what the pilot is for. Start writing the theory chapters this week.

OutputPilot corpus, gate report, first draft of chapters 1–2.
Gate A — go / no-goAll six gates green on pilot data, and the tripwire's surviving features each have a written protocol derivation. If not: fix the testbed and re-pilot. Do not proceed on hope.
W6–8~80 h wall, ~15 h hands-on

Full capture campaign

Two epochs — A in weeks 6–7, B in week 8 — giving a genuine temporal split. Target 40,000 negative and 8,000 positive flows, plus a ~3,000-flow live-Tor validation set. Run gates nightly on the accumulated corpus so a drift is caught in hours, not weeks. Keep writing while it runs.

OutputThe corpus, a manifest, a hash list, and an attrition table with per-class drop reasons.
W9~30 h

Dataset build and split protocol

build_dataset.py v2 emitting four split axes from one corpus: unseen connection, unseen destination, unseen profile, unseen epoch. All keyed on conn_id. Fix cross_validate.py: carry groups through the same permutation as features, group by connection, select epochs on an inner fold.

Models and the generalisation matrix

Retrain the three existing models — plus a fourth "model" that is the trivial rule ≥50% of upstream records are exactly 558 B. Produce the generalisation matrix: four split axes × four models, each cell reporting TPR at fixed FPR with Clopper–Pearson bounds, average precision, and effective n.

OutputThe central results table of the thesis, plus a DET curve that stops at 1/N.

07

The story gets stronger, not weaker

The v1 failure is an asset if you publish it as a method. Most theses cannot demonstrate that their pipeline is leak-free; you will be able to show the receipts.

The current narrative is "we built a classifier and it gets 99%". That is unfalsifiable and a committee knows it. The v2 narrative is:

  • We built a measurement apparatus and validated it adversarially. Here is the gate suite, here is what it rejected, here is the corpus it accepted. Include a short section on the v1 corpus and how the harness detected the leak — that is scientific maturity, and it converts the strongest attack on the thesis into a chapter.
  • WebTunnel carries one hard invariant. 558 B on the wire = 5 (TLS header) + 514 (Tor cell) + 22 (WebSocket framing) + 1 (inner content type) + 16 (AEAD tag), with the 2× multiple at 1072 B. It survives handshake removal, connection independence, destination change and network profile. A two-instruction rule exploits it — no ML needed. That is a genuine, citable protocol result and it is the thesis's contribution.
  • Detection is cheap at the flow level and still hard at the network level. The measured FPR bound below 10⁻⁴ against 40,000 negatives, and the base-rate analysis showing what that does and does not buy at ISP scale. This is the assignment's core question, answered with evidence.
  • Padding is not a defence; distribution relocation is. Static-adversary and adaptive-adversary results side by side, with the mechanism: 1–128 B moves 558 B to 559–686 B, which never enters the legitimate upstream support of 40–81 B. A defence must move the distribution into that support — MTU-sized coalescing plus injected HTTP/2 control chatter (WINDOW_UPDATE, PING, SETTINGS) to reproduce the small-record mass every legitimate class has and WebTunnel entirely lacks. Concrete, testable, and independently corroborated by Huma (NDSS 2026).

None of that requires novelty. It requires the claims to match the evidence — which is exactly the "solid and safely defensible" target.

08

Scope discipline and risk

You have four months, which is enough — provided you spend none of it on the five things below.

Do not do these

  • Do not pre-train a Transformer.Your own roadmap correctly identified this as unrealistic. The lightweight sequence model already satisfies the assignment's "např. 1D-CNN, TrafficFormer". Keep it as a secondary model and spend nothing more on it.
  • Do not invent a novel defence.Evaluating two known defence families honestly against an adaptive adversary is worth more marks than a new one evaluated badly — and it is the difference between a chapter that holds and one that collapses under one question.
  • Do not chase FPR = 10⁻⁵ or 10⁻⁶.600+ hours of capture for a number you can present as a projection. Measure 10⁻⁴, project the rest, say which is which.
  • Do not add a fourth ML model.Add the trivial 558 B rule instead. It costs an afternoon and it is a stronger scientific anchor than any additional network.
  • Do not rewrite in a new language or framework.The Python stack is fine. The only new code outside Python is the Go traffic client, and only because uTLS parity requires it.

Risk register

  • uTLS parity turns out to be harder than expectedThe WebTunnel client may not expose a uTLS option in the build you are using. Mitigation: fall back to strict handshake removal (hs_end_idx) plus G1 relaxed to "post-handshake only", and report the stock-Go-fingerprint discovery as a finding in its own right. Decide this in week 2, not week 10.
  • chutney adds a week you don't haveMitigation: it is optional. Keeping the live Tor network is acceptable if you also route the negatives through matched per-destination netem delay so RTT is not class-informative — and state the reproducibility limitation explicitly. Decide by end of week 3.
  • Gate A fails repeatedlyThe most likely cause is budget parity (G4): making a chat session move 80 KB in 4 s takes generator work. Mitigation: a hard stop after three pilot iterations — then narrow the budget distribution rather than widening the gate, and document the narrowed range as a scope limitation.
  • Capture throughput is lower than 500 flows/hConnection-per-sample adds TLS setup to every sample. Mitigation: parallel client containers; and 30,000 negatives (FPR ≤ 10⁻⁴) rather than 40,000 is still a full-strength claim. Measure the real rate during the pilot and size the campaign from that number, not from this document's estimate.
  • Everything slips by three weeksMitigation: the theory chapters are written from week 5 and depend on nothing. Weeks 12 and 16 carry the slack; cut the cascade chapter before you cut a gate.
09

What to do on Monday

The whole plan hinges on doing one counter-intuitive thing first: write the tests before you fix anything. Concretely, in this order:

  • git tag v1-audit && git push --tags — freeze the state the audit refers to.
  • Write contracts.py with the two dataclasses above. Nothing else. Half a day.
  • Write checks/tripwire.py: fit a depth-1 stump per feature, print AUC and threshold, sorted. Run it on your existing tabular_dataset.npz and read the output. That table is the first figure of your new chapter 4.
  • Write checks/null_controls.py — label shuffle, and same-generator/different-label. Watch them pass on shuffled labels and fail informatively on the real ones.
  • Then, and only then, open collect_scaled_dataset.py.

By Friday you will have a harness that objectively describes what is wrong with the current corpus, which is what makes every subsequent decision easy — including the ones this plan gets wrong.

On the recommendation

Refactor rather than restart, because the failure is concentrated in the two lowest layers and the expensive layers above are sound. But treat those two layers as a rewrite with a new contract, not as a series of patches — patching a wrong unit of analysis is how the same bugs come back under different names. The schedule is dominated by unattended capture time, which means the real risk is not effort but sequencing: the harness must exist before the campaign, and the campaign must not start until a pilot passes it. Everything else in this plan is negotiable.
